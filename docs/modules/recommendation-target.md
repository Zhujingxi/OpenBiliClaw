# Recommendation Pipeline

`openbiliclaw.recommendation` contains the deterministic discovery-to-history pipeline. Candidate state is explicit (`discovered → normalized → prefiltered → evaluated → admitted → selected → shown → interacted/expired`, with terminal rejection) and every transition is checked in Python and enforced by a SQLite transition trigger. Rejections and admissions have dedicated immutable audit tables; selection persists evaluated → admitted → selected atomically. Delivering the Application feed atomically records a deterministic `shown_id` and moves selected → shown; accepted feedback validates that shown record and matching content before moving shown → interacted.

Discovery plans bounded provider-neutral queries from the canonical `default` profile's `DiscoveryProfile`, falls back to deterministic defaults when `recommendation.query` is unavailable, and calls typed provider search capabilities directly. Content-dimension preferences feed discovery interests until the stable-interest analyzer is routed. Discovered previews retain their plan topic as candidate provenance. Hard prefilters apply profile avoidances before the one-shot `recommendation.evaluate` contract; selection applies hard negative topics, then uses named model/freshness/novelty contributions plus fixed provider (2), creator (1), and topic (2) quotas.

The production baseline evaluator is deliberately deterministic and not personalized: accessible candidates receive the same model contribution, then freshness and novelty determine rank. Profile influence currently shapes acquisition query/topic and hard exclusions, not model scoring. Optional `recommendation.expression` stores copy provenance separately and falls back to safe deterministic text.

`RecommendationService.feed()` is model-free and joins selected candidates with their immutable expression reason. It orders the newest run by stored rank and returns score contributions for explainability. Refill processes only newly inserted deterministic candidate IDs; rediscovery of an all-known batch is a successful observable no-op rather than a state retransition. Public refresh bounds discovery with `maximum_items`; scheduled replenishment uses the configured pool target. Discovery, evaluation, expiry and replenishment are Core `JobSpec`s with explicit timeout, resource and non-overlap policies, and host job health comes from `RuntimeSupervisor`.

Recommendation discovery remains text-query based. There is no semantic retrieval consumer, durable provider projection body, or embedding index. L4 deliberately added no speculative semantic table; an index will be designed when a semantic discovery query API exists.

Production composition registers discovery, evaluation, expiry, and replenishment jobs. Feedback enters the Observation workflow; deleted legacy discovery/recommendation engines and producers have no compatibility path. Offline domain evaluation scenarios remain deferred.
